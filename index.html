How I work a run

  1. Tag it. Every test carries @smoke, @regression, and a feature tag, so a quick check or a full run is one filter away.
  2. Read the failures. I open the trace for each failure and sort it: real app defect, or an environment or data issue.
  3. Close the loop. Defects get reported with the trace as evidence, then re-run once they're fixed.

Beyond testing the app, I also helped change it. I made frontend changes in the product's web app, then QA'd my own work end to end.

TC-02 · Manual QA

Manual Regression & Exploratory Testing

Every ticket passes through QA before it ships. This is the loop I ran each sprint, and the kinds of tickets that went through it.

The QA loop

  1. In progress

    Dev picks up the ticket

  2. QA Ready

    Change is on staging and handed to me

  3. Testing

    Test cases, regression, exploratory checks

  4. QA Approved

    Passes, or goes back with a bug report

  5. Done

    Shipped

Kinds of tickets I QA'd (paraphrased)

  • BugSearch and filtering breaks on table pages 2+QA Approved
  • BugTotals don't match between summary and tableQA Approved
  • BugStatus doesn't update after saving from an edit dialogQA Approved
  • FeatureUsers can switch between multiple practicesQA Approved
  • FeatureKeyboard shortcuts on the claim summary pageQA Approved
  • FeatureAssign work to an external userQA Ready
  • UIRename a sidebar section to match new terminologyQA Approved
  • AutomationReview E2E automation for a feature ticket, then mergeDone

What I look for

  • Happy pathDoes the feature do what the ticket says?
  • EdgesEmpty states, invalid input, pagination, permissions
  • RegressionDid anything nearby break?
  • DataDoes the UI match the database and the business rules?
  • EvidenceClear reproduction steps and screenshots in every report
  • RetestVerify the fix on staging, then approve
